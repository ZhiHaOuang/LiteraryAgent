### 裁剪原则与每批交付

Runtime 精简以降低产品耦合、依赖负担和后续维护范围为目标，优先删除明确不采用的上游产品功能、重复入口及其专属依赖，不以“与 Coding 有关”作为删除依据。模型—工具循环、会话与并发、工具调度、文件搜索与编辑、受限脚本执行、隔离、审批、取消和恢复原则上保留，并补充文学任务的上下文、身份、预算、授权和状态语义。

保留实现、纳入发布包、授权某个任务使用是三个独立层次。任务能力由产品控制，正式故事状态不得通过通用工具绕过 Kernel。当前写作任务的工具限制继续有效；扩大暴露范围要先验证隔离和写入门禁，不能用新增提示词代替。

每批明确：删除什么及原因、退出哪些调用和专属配置、保留机制的测试、源码/构建/运行产物身份、CLI/Extension 实际使用的产物、回退步骤。维护收益看改造通用机制时需要理解和修改的无关模块是否减少，不用删行数或文学评分替代。

### 已知来源的当前复核与直接关联查询

`source_review.py`／`ProjectStore.generation_source_review` 复核确切版本捕获的来源：当前、变化、
不可用、未知、仅索引和历史版本。Live 的两种方向读取与 Story 按各自投影重算，事实同样区分
结构化返回与实际渲染片段。正式方向未换选择时，再生成备选方案不误报；同 ID 的事实修改可见。
普通活动正文检查版本替换，显式旧候选只核对该版本是否仍可用，不假定生成时的活动版本。

`source_impact.py`／`ProjectStore.source_impact` 从文档查询已知直接关联，分开事实／提案的声明来源、
正式选择的声明来源、实际捕获输入及编辑基础。文档索引不当作正文输入，编辑基底也不当作已读证明。
不指定版本时查该文档各版本的已知关联，指定时只匹配确切版本；方向方案集与最新 head 分开。
场景卡独立可变，关联不绑定正文版本。版本条目同时显示 state 与 is_active，不把历史 accepted 当当前正文。

查询使用同一 SQLite 读取快照，逐项扫描而不复用最多 1000 版的列表接口；每表最多 5000 项，
结果上限与扫描上限分开，截扫描时 discovered 仅为已发现数量。无来源旧记录、损坏记录、未知投影和
省略部分保持未知，不能据此判断“后文全部无影响”。不新增数据库或自动修复、撤销、传递改写。

只读 `studio_source_impact`／Studio `source-impact` 通过现有 Backend 和 CLI；
`studio_review_context` 在当前 snapshot／指纹之外附加 `generationSourceReview`，
候选详情展示同一单版本复核，不自动扫描全书。没有新写 grant 或隐式采用门槛；React 布局不变。

## 人物／读者认知基础批次

`narrative_knowledge.py` 复用现有文档／版本管理认知提案、精确历史提案确认和撤回，
类型为 `narrative_knowledge`，所有普通版本保持 draft。确认是独立的内容指针；再次提案不覆盖确认，
撤回没有历史回退。人物的 knows／believes／uncertain 是作者标注，允许误信，不提升为 Canonical。
`managed_documents.py` 统一两类受管理文档的通用写入保护，不改变旧方向的错误语义。

`narrative_view.py` 提供已登记记录的双轴只读投影：人物按 story 坐标，读者按 reading 坐标，
均由作者显式给定整数，不解析章节序号或自由时间标签。区间为 [from_position, until_position)，
同一观察者／主题的确认区间不得交叠；不同观察者可存在信息差和相反信念。
先按人物和起点过滤再扫描预算。来源过期时保留确认，只提供待复核 ID，不暴露其正文；
无来源声明明确为 unbound。旧事实、人物档案、参与事件和未来规划不会自动转成认知记录。

Studio／CLI／Backend 共用 knowledge、knowledge-view 读取及 propose／confirm／withdraw 写入。
确认和撤回经独立创作权限；knowledge 任务精确绑定动作、当前 head、指定提案和一次写入。
资料库沿用现有 React 布局，新增确认／撤回动作；Python 与 TS 协议枚举同步，旧预览和不完整详情不可提交。
`source_impact.py` 仅把 confirmed.sources 纳入已知直接关联，新提案不替换原确认的声明依赖。

本批 scope 为 registered_records_only，registered_filter_applied=true、model_input_isolation=false。
不把作者全局读取改为受限阅读；尚未隔离 router、会话历史、指令、通用工具、专家及工作流输入。
下一批先为全新、无历史、无工具的阶段绑定宿主视图，再捕获实际供应商请求验证必要信息召回与禁止信息泄漏；
不通过新增提示词或只检查工具返回来宣称完成隔离。Core 与 Native 工程测试使用本地合成模型，不证明文学质量。

## 下一阶段的架构重构顺序

以下阶段尚未由本次文档更新实现。按可验收的行为拆批，不按文件数量拆批；每批先复用现有服务，确认耦合后再抽取模块。

当前主路径已经接入共享 Backend，Native Runtime 也已有真实 MCP 候选写作与审批验证。规划、选区改稿、审读、采纳的四路径矩阵已通过；正式方向已有选择、撤回及审读来源绑定。实际生成输入已有部分捕获、原记录继承与已知直接关联的只读复核；人物／读者认知已有显式记录与双轴投影，完整语义影响、传递依赖、作者重新裁决及实际模型输入隔离仍需推进。下面 B–F 保留长期职责划分，不要求每项一般维护或全部 Core 工具对齐完成后才推进文学能力。

兼容入口定位已由作者确认：`native.launch_native` 保留 Rust TUI，`app_server.main` 保留 Core stdio 协议；本次验收主 CLI／Extension，不把这两个入口算作统一 Backend。未来若另行决定迁移，需要协议适配与端到端任务验收，不能直接把 Core 客户端连接到 `lg.backend.v1`。显式开发用 `code` 路径及 Backend 内部 worker 不是同类产品入口缺口。

总请求预算作为独立改动设计：保留 `max_stage_context_chars` 的原语义；新上限必须明确单位、默认兼容行为以及每次外发的覆盖路径。完整请求包括指令、历史、工具结果、工具定义和输出 Schema，不能把字符／字节称为 token，也不能用单次请求上限宣称控制会话总成本。Core 的完整请求需要在供应商 bridge 核对，单靠阶段 host 输入无法观察 Core 增补的历史和工具。

## 叙事上下文后续批次的最小范围

先在 LitIsLand 最新副本复现三项读取问题，为既有上下文入口明确“面向作者全局规划”与“面向当前叙事位置”的用途。设计参数至少包含任务用途、目标版本、视角、故事时间、阅读截止和预算；宿主绑定读取身份，模型不能通过参数切换到更宽的视图。

结果应携带来源版本、有效性、截断状态和缺失信息。先解决事实状态与来源状态的真实表达，不静默删除已确认事实，也不把修改来源等同于事实必然错误。完整认知投影依赖数据基础，不能仅凭过滤章节号就宣称完成。

主要候选改动位置是 `project_store.py`、`story_context.py`、`writing_mcp.py` 及调用它们的阶段入口；测试分别覆盖存储、工具和实际模型输入。具体新接口、迁移策略和最终文件范围以这轮最小实验为准。本文件不是要求立即创建一套平行 Kernel 或新的故事数据库。

首批读取修复复用上述模块和 `StoryWorkflowService`，增加事实来源状态、作者视图元数据、准确场景候选版本及正文位置过滤。完整人物／读者知识、倒叙时间投影和会话历史隔离未由这一批完成；不能把前文正文过滤当作完整叙事可见性门禁。

Rust TUI 只读审查确认上游已有远程 app-server 客户端，品牌 standalone 入口仍传入空 remote endpoint；Unix socket 上也使用 WebSocket，不能直接接入 JSONL Backend。作者已选择保留独立兼容入口，本阶段不新增适配、构建或删除 TUI；未来迁移另行定义范围。

## 作者控制与审美判断

正文候选、事实提案、剧情方案和正式长期规划需要明确区分。作者请求构思、比较、试写或保存候选，不自动授权正式选择。创作批准绑定具体目标、内容、基础版本和范围；保留作者显式配置的预授权策略，模型不得扩大其含义。

权限、来源、版本、身份和幂等属于硬约束。人物成长、伪装、情绪反常、节奏与文风通常属于可讨论的文学判断。审读提供证据、疑点与替代方案，作者保留裁决权；不默认用模型审美分数禁止创作。

## 进度与质量的评价方式

| 方向 | 持续记录的证据 |
| --- | --- |
| 叙事一致性 | 人物越界认知、时间冲突、世界事实矛盾；结构化信息泄漏与正文语义错误分开测 |
| 作者控制 | 未授权采纳/规划改变、选区越界、过期批准复用和重复提交；目标为零 |
| 上下文质量 | 必要信息召回、禁止信息泄漏、有效来源覆盖、Token 与延迟；空上下文不算成功 |
| 工具有效性 | 无效/重复调用比例、恢复成功率、完成任务的总调用与费用 |
| 长期可靠性 | 旧章修改的影响召回与误报、陈旧制品阻断、取消和崩溃恢复 |
| 文学质量 | 相同模型/参数/材料下的人类成对盲评，分别评情节、人物、张力、表达 |
| 协作体验 | 达到作者认可所需的干预轮次、工作时间、重做与重复说明次数 |

对照组至少包括通用 Coding Agent、当前 LG 和机制实验版。先在相同预算下比较，再报告放宽成本时的质量变化；不能把额外模型调用产生的收益全部归因于架构。反馈需带适用作品与范围，不从单次修改自动泛化成作者长期偏好。
